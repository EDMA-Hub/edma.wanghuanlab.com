# 企业数字化产品组合与落地路线规划

> 文档状态：规划基线 v1.1  
> 更新日期：2026-09-23  
> 适用对象：公司管理层、产品负责人、架构负责人、交付负责人  
> 说明：本文用于定义产品边界与实施顺序，不等同于已承诺的产品范围、工期或报价。所有周期和指标需在客户调研后基线化。

## 一、结论摘要

建议对外采用“**1 个统一数字化平台 + 5 大业务套件 + 23 个业务应用**”的产品结构，而不是把 23 个缩写并列为 23 套彼此独立的系统。

- **统一数字化平台**负责身份、权限、流程、主数据、集成、数据分析等公共能力。
- **五大业务套件**按企业价值流和责任域组织，便于客户理解、销售组合和项目分期。
- **23 个业务应用**保留专业名称和独立入口，但统一账户、数据标准、交互规范和运维体系。
- 应用之下再拆**业务模块与能力项**；部署时按业务边界组合，不按每个英文缩写机械拆成微服务。

推荐的五大套件如下：

| 产品套件 | 业务应用 | 应用数 | 核心价值链 |
| --- | --- | ---: | --- |
| 客户与渠道运营 | CRM、CDP、OMS、POS、DMS | 5 | 获客、成交、订单、门店和经销商协同 |
| 产品与制造运营 | PLM、MRP、APS、MES、QMS、EAM | 6 | 产品定义、计划排程、生产执行、质量和设备 |
| 供应链与物流 | SRM、WMS、TMS | 3 | 供应商协同、仓储作业和运输交付 |
| 企业经营与协同 | ERP、HRM、OA、EDMS | 4 | 经营核算、组织人事、办公协同和受控文档 |
| 数字化平台 | IAM、BPM、MDM、iPaaS、BI | 5 | 统一身份、流程、主数据、集成和分析 |

其中，渠道管理保留 **DMS（Dealer/Distribution Management System）**，文档管理使用 **EDMS（Electronic Document Management System）**，避免两个 DMS 在产品命名、搜索、合同和项目沟通中产生歧义。

## 二、产品层级和命名规则

### 2.1 四层产品模型

| 层级 | 定义 | 示例 | 对外呈现 |
| --- | --- | --- | --- |
| 平台 | 全产品共享的技术与数据底座 | 数字化平台 | 品牌总架构、技术能力 |
| 套件 | 面向一个完整业务域的产品组合 | 产品与制造运营 | 官网一级分类、方案和报价组合 |
| 应用 | 有清晰用户、业务目标和边界的产品 | MES、WMS、CRM | 可独立采购、授权和进入 |
| 模块/能力 | 应用内部的可配置功能单元 | MES 工单执行、报工、追溯 | 需求清单、版本和许可明细 |

官网展示 23 个应用是合理的；但在产品、研发和交付体系中，不应把“23 个名称”直接等同于“23 个代码仓库、23 套数据库或 23 支团队”。产品边界、部署边界和团队边界可以相关，但不必完全一致。

### 2.2 对外命名原则

1. 一级使用中文价值名称，例如“产品与制造运营”。
2. 二级保留行业通用缩写，例如“MES 生产执行”。
3. 容易重名的缩写必须消歧，例如 EDMS 与渠道 DMS。
4. 商业合同同时写明“套件、应用、模块、用户/组织范围、环境和服务”。
5. 产品命名不承担全部架构说明；边界以能力清单、主数据归属和接口契约为准。

## 三、五大套件的责任边界

### 3.1 客户与渠道运营

面向销售、市场、门店、客户服务和渠道团队，回答“客户是谁、需求如何转化、订单如何履约、渠道如何协同”。

- **CRM**：客户关系、线索、商机、销售活动、合同与服务过程。
- **CDP**：客户行为事件、身份融合、标签、分群和运营激活。
- **OMS**：多渠道订单接入、拆合单、库存预占、履约路由与售后。
- **POS**：门店开单、收银、会员、促销、班次与门店库存动作。
- **DMS**：经销商准入、授权、渠道订单、库存协同、返利和渠道考核。

边界要点：CRM 管“关系和销售过程”，CDP 管“行为与人群”，OMS 管“订单编排”，POS/DMS 是订单和渠道现场。财务记账、应收、成本与税务仍由 ERP 负责。

### 3.2 产品与制造运营

面向研发、工艺、计划、车间、质量和设备团队，回答“生产什么、用什么生产、何时生产、如何执行、是否合格、设备是否可用”。

- **PLM**：物料、BOM、图纸、工艺、产品版本和工程变更。
- **MRP**：需求展开、净需求、采购/生产建议与物料齐套。
- **APS**：有限产能排程、约束计算、插单模拟和计划发布。
- **MES**：工单下达、派工、报工、在制品、追溯和现场采集。
- **QMS**：质量标准、检验、偏差、不合格、CAPA 和质量分析。
- **EAM**：设备台账、点检、保养、维修、备件和设备绩效。

边界要点：PLM 定义产品，MRP 计算物料，APS 决定时序，MES 负责执行，QMS 负责质量治理，EAM 负责设备生命周期。ERP 接收计划与执行结果用于采购、库存、成本和财务核算。

### 3.3 供应链与物流

面向采购、供应商、仓库与物流团队，回答“谁来供、货在哪里、如何准确送达”。

- **SRM**：供应商准入、寻源、报价、绩效、协同与风险。
- **WMS**：库位、收货、上架、波次、拣选、复核、盘点和库存移动。
- **TMS**：承运商、运力、路线、装载、运单、轨迹、签收与运费结算依据。

边界要点：ERP 持有采购/销售业务单据和库存财务账；WMS 持有仓内实物动作；TMS 持有运输执行；SRM 持有供应商关系与协同过程。

### 3.4 企业经营与协同

面向财务、人力、行政和全体员工，回答“企业如何核算、组织如何运转、事项如何协同、文件如何受控”。

- **ERP**：财务、采购、销售、库存、成本和经营核算主账。
- **HRM**：组织、人员、岗位、入转调离、考勤薪酬与人才过程。
- **OA**：门户、事项、会议、公告、日常审批和协作工作台。
- **EDMS**：受控文件、版本、权限、发放、签阅、水印、归档和保留策略。

边界要点：OA 是员工工作入口，不应复制每个业务应用的流程和数据；EDMS 是文件权威库，不取代 PLM 对产品结构与工程变更的管理。

### 3.5 数字化平台

这是跨套件复用能力，而非一个“大而全的后台”。

- **IAM**：统一认证、单点登录、用户生命周期、角色与权限策略。
- **BPM**：跨系统审批、业务流程编排、任务中心与流程监控。
- **MDM**：客户、供应商、物料、组织等主数据标准、编码、质量和分发。
- **iPaaS**：API、消息、文件、连接器、映射、编排和集成监控。
- **BI**：指标口径、语义模型、自助分析、驾驶舱和数据权限。

边界要点：IAM 解决“谁能访问”，BPM 解决“人和业务事项如何流转”，iPaaS 解决“系统如何交换数据”，MDM 解决“关键实体以谁为准”，BI 解决“如何形成一致分析口径”。

## 四、容易冲突的领域与唯一权威源

产品之间存在业务关联是正常的，真正需要避免的是“同一对象被多个系统同时当作最终权威”。建议为关键对象明确 System of Record（SoR，权威记录系统）。

| 对象/过程 | 建议权威系统 | 其他系统的职责 | 必须写清的规则 |
| --- | --- | --- | --- |
| 客户主体与统一编码 | MDM | CRM 维护关系，CDP 融合身份和行为，ERP 管财务属性 | 新增、合并、停用、冲突仲裁 |
| 联系人和销售关系 | CRM | CDP 使用身份映射，OMS 使用履约联系人 | 联系人与客户主体的关联规则 |
| 客户行为与标签 | CDP | CRM/BI 消费结果 | 事件定义、标签口径、失效时间 |
| 物料与分类标准 | MDM/PLM | ERP 使用采购和核算属性，MES/WMS 使用执行属性 | 创建入口、审批、版本和下发时点 |
| BOM、图纸、工程版本 | PLM | ERP/MRP/MES 消费已发布版本 | 生效日期、变更影响、旧版处置 |
| 销售订单编排 | OMS | CRM 发起机会/合同，ERP 形成经营单据，WMS 执行出库 | 状态映射、取消/拆分、幂等 |
| 财务凭证、应收应付、成本 | ERP | 其他系统提供业务事实 | 过账时点、冲销、期间和币税规则 |
| 仓内实物库存 | WMS | ERP 记库存账与成本，OMS 汇总可售视图 | 批次/序列、冻结、盘点差异 |
| 生产物料计划 | MRP | APS 使用供需结果，ERP 承接采购/生产建议 | 计划版本、冻结区和重算条件 |
| 详细生产排程 | APS | MES 接收已发布排程 | 约束、锁定、插单和回滚 |
| 生产现场事实 | MES | ERP 接收产量消耗，QMS 接收质量事件 | 工单状态、报工、采集时间和更正 |
| 质量标准与闭环 | QMS | MES 采集检验数据，PLM 接收设计反馈 | 检验版本、不合格、CAPA 关闭条件 |
| 设备运维记录 | EAM | MES 使用设备状态，ERP 管固定资产财务价值 | 设备编码、停机、备件与资产映射 |
| 供应商生命周期 | SRM | MDM 管统一编码，ERP 管采购交易和应付 | 准入、绩效、冻结和分级 |
| 组织与员工 | HRM | IAM 建账号和权限，MDM 分发组织标准 | 入转调离触发、外部人员和历史组织 |
| 受控文件 | EDMS | PLM/QMS/OA 关联文件和业务对象 | 版本、发布、回收、保留与审计 |
| 流程实例与任务 | BPM | OA 提供工作台，各应用提供业务表单与规则 | 流程归属、业务事务和失败补偿 |
| 跨域分析指标 | BI | 业务应用提供明细和实时运营看板 | 口径、血缘、刷新频率和权限 |

## 五、落地服务划分

这里的“服务”同时包含两层含义：对客户交付的专业服务，以及产品内部的服务边界。两者应分别规划，避免用技术微服务直接代替项目服务目录。

### 5.1 面向客户的交付服务包

| 服务包 | 主要工作 | 核心交付物 | 建议验收方式 |
| --- | --- | --- | --- |
| 01 业务蓝图与价值诊断 | 访谈、现场走查、痛点与目标、范围和优先级 | 现状图、目标蓝图、能力差距、路线图、业务指标基线 | 管理层与业务负责人联合签字确认 |
| 02 产品方案与配置实施 | 套件选择、组织/角色、参数、表单、规则和流程配置 | 方案设计、配置清单、原型、权限矩阵 | 关键场景原型评审与 UAT |
| 03 主数据治理 | 标准、编码、清洗、去重、责任制和发布流程 | 数据标准、数据字典、质量规则、责任矩阵 | 抽样质量、重复率、必填完整率和审批流程 |
| 04 集成与接口 | 系统盘点、接口契约、消息/API/文件集成、异常处理 | 接口清单、契约、映射、错误码、监控面板 | 端到端场景、重试、幂等和对账测试 |
| 05 数据迁移 | 范围、清洗、转换、试迁移、冻结、切换和回退 | 迁移策略、映射、批次报告、对账和回退方案 | 业务对账、财务对账、抽样追溯 |
| 06 试点与推广 | 试点单位、超级用户、培训、切换、问题闭环 | 推广计划、培训材料、作业指导书、上线检查表 | 试点连续运行、关键角色掌握度、问题关闭率 |
| 07 测试与质量保障 | 单元、集成、性能、安全、UAT 和回归 | 测试计划、用例、缺陷报告、上线质量门禁 | 阻断缺陷清零，关键场景通过 |
| 08 运维与安全保障 | 监控、备份、容灾、补丁、账号审计和应急响应 | 运维手册、SLA、监控告警、演练记录 | 恢复演练、告警闭环、权限审计 |
| 09 持续优化与运营 | 使用分析、流程优化、指标复盘、版本迭代 | 运营月报、优化清单、季度路线图 | 采用率、流程周期、数据质量等趋势复盘 |

服务包可以按阶段采购，也可以组合成“蓝图—实施—上线—运营”的完整交付。验收指标必须在项目启动时确定当前值、目标值、取数口径和责任人，不能在上线后再补定义。

### 5.2 产品内部的公共平台服务

建议优先建设以下共享能力，避免五个套件重复造轮子：

1. 租户、企业、组织与环境管理。
2. 统一登录、用户生命周期、角色和数据权限。
3. 菜单、工作台、待办、通知和消息模板。
4. BPM 流程、审批、任务、委托和超时升级。
5. 主数据编码、标准、质量、审批和分发。
6. API 网关、连接器、事件总线、任务调度和集成监控。
7. 文件、附件、预览、电子签名、水印和归档基础能力。
8. 审计日志、操作留痕、配置变更和合规导出。
9. 搜索、导入导出、规则、字典、国际化和打印模板。
10. 指标语义、数据权限、数据服务和分析门户。

公共能力要“薄而稳定”。各业务域特有的状态机、校验规则和业务事务仍留在领域应用中，不能全部塞进 BPM、MDM 或低代码平台。

### 5.3 领域服务与初期部署单元

规划阶段不建议直接拆成 23 个独立微服务。更稳妥的起步方式是“领域模块化 + 6～8 个可独立部署单元”，随团队规模和负载再拆分：

| 建议部署单元 | 初期包含内容 | 后续可能拆分条件 |
| --- | --- | --- |
| 访问与网关 | IAM、API 网关、租户和入口 | 多区域部署、外部生态调用显著增长 |
| 平台公共服务 | BPM、MDM、通知、文件、审计、任务调度 | 某能力形成独立产品或负载/团队独立 |
| 客户与订单域 | CRM、OMS、渠道/门店接口 | 订单吞吐与客户运营迭代节奏明显分化 |
| 企业经营域 | ERP、HRM、OA、EDMS | 财务合规或人力数据隔离要求提高 |
| 计划与制造域 | PLM 接口、MRP、APS、MES、QMS、EAM | 排程计算、现场高可用或边缘部署需要独立 |
| 供应链执行域 | SRM、WMS、TMS | 仓库数量、自动化设备或运输网络扩大 |
| 数据与分析域 | 数据采集、语义模型、BI、CDP 分析 | 数据量、实时计算和算法团队独立 |
| 集成运行域 | iPaaS 运行时、连接器、消息和对账 | 客户连接器数量及外部系统复杂度增长 |

这不是固定的最终架构。拆分必须由独立扩缩容、故障隔离、数据合规、交付节奏或团队所有权驱动，而不是为了追求“微服务数量”。

## 六、技术架构设计

### 6.1 架构目标与约束

技术架构首先服务于制造企业的业务连续性、可实施性和长期升级，而不是追求技术组件数量。建议以以下目标作为架构评审基线：

1. **统一而不耦合**：统一身份、组织、主数据、接口和运维标准；业务域保持独立模型和发布节奏。
2. **总部与现场兼容**：总部业务适合中心化部署，MES、WMS、设备采集等现场场景需考虑边缘节点、弱网和断网续作。
3. **渐进式拆分**：先建立清晰的领域模块和数据所有权，再按实际负载、团队和交付要求拆成独立微服务。
4. **默认可观测**：接口、消息、批处理和业务状态从第一版开始具备日志、指标、链路和对账能力。
5. **安全内建**：身份、权限、审计、密钥、数据保护和供应链安全进入研发流程，而不是上线前补做。
6. **可配置但不过度平台化**：组织、表单、流程、规则和字典可配置；领域核心状态机与核算规则仍由代码和测试保护。
7. **支持持续升级**：标准产品与客户扩展分离，避免每个客户形成不可合并的代码分支。

需同时接受的现实约束包括：客户可能已有金蝶、用友、SAP 等 ERP；工厂网络与设备协议不统一；项目需要支持 SaaS、私有化或混合部署；部分现场系统不能依赖公网持续在线。因此架构必须支持“替换、共存、集成”三种实施模式。

### 6.2 总体逻辑架构

建议采用六层逻辑架构。层与层之间通过明确接口交互，上层不能绕过服务接口直接修改下层或其他领域的数据。

```text
┌─────────────────────────────────────────────────────────────┐
│ 体验与渠道层                                                │
│ Web 管理端｜移动端｜门店 POS｜车间终端｜供应商/经销商门户    │
├─────────────────────────────────────────────────────────────┤
│ 访问与编排层                                                │
│ CDN/WAF｜负载均衡｜API 网关｜BFF｜统一认证｜开放 API          │
├─────────────────────────────────────────────────────────────┤
│ 业务领域层                                                  │
│ 客户渠道｜产品制造｜供应链物流｜企业经营｜协同办公            │
├─────────────────────────────────────────────────────────────┤
│ 公共平台层                                                  │
│ IAM｜BPM｜MDM｜文件｜通知｜审计｜规则｜任务调度                │
├─────────────────────────────────────────────────────────────┤
│ 集成与数据层                                                │
│ iPaaS｜消息总线｜CDC/ETL｜数据仓库｜指标语义｜BI               │
├─────────────────────────────────────────────────────────────┤
│ 基础设施与运维层                                            │
│ 容器平台｜数据库｜缓存｜对象存储｜可观测｜备份容灾｜DevSecOps  │
└─────────────────────────────────────────────────────────────┘
```

各层责任如下：

| 层级 | 核心责任 | 主要边界 |
| --- | --- | --- |
| 体验与渠道层 | 面向不同岗位提供任务化交互 | 不持有核心业务真相；通过 BFF/API 调用领域服务 |
| 访问与编排层 | 流量入口、认证、限流、协议转换和页面聚合 | 不承载领域核算规则，不直接访问领域数据库 |
| 业务领域层 | 承载订单、计划、生产、仓储、财务等业务规则 | 每个领域维护自己的模型、事务和数据所有权 |
| 公共平台层 | 提供跨领域可复用的稳定能力 | 不吞并领域状态机，不成为万能业务后台 |
| 集成与数据层 | 系统连接、事件传输、数据加工和分析 | 集成不改写源系统业务规则，分析不反向充当交易主库 |
| 基础设施与运维层 | 运行、交付、安全、监控和灾备 | 通过标准化能力降低应用团队运维负担 |

### 6.3 应用访问与前端架构

- 管理端建议采用 **Vue 3 + TypeScript + Vite**，建立统一设计系统、权限指令、表格/表单规范和微前端接入规范。
- 首期不建议为了技术统一而立即采用微前端。只有不同团队需要独立发布、页面规模显著增长或存在外部应用接入时，再引入模块联邦或基座式微前端。
- 面向角色建立工作台和任务入口，不把 23 个应用简单做成 23 个孤立菜单。
- 对移动端、POS、PDA、车间工位等特殊终端分别提供轻量客户端或响应式界面，共享认证和 API 契约，不强求共享全部 UI 代码。
- BFF 只负责页面聚合、字段裁剪和协议适配；订单、库存、权限判断等领域规则必须下沉到对应服务。

### 6.4 后端与服务架构

推荐采用领域驱动设计的模块化服务架构：

- 业务服务基线可采用 **Java 21 + Spring Boot 3**，通过统一脚手架提供鉴权、日志、幂等、异常、审计和可观测能力。
- 对外业务接口优先使用 REST + OpenAPI；内部高频且强类型的调用可在确有收益时使用 gRPC，不在首期混用多套 RPC 框架。
- 长流程和跨域状态传播优先使用领域事件；需要立即反馈的校验、查询和命令使用同步 API。
- 领域服务内部按“接口层—应用层—领域层—基础设施层”组织，避免 Controller 直接调用数据库形成贫血脚本系统。
- 批处理、计划计算、报表生成和文件解析与在线交易隔离线程池和资源配额，必要时独立为 Worker。
- 设备协议解析放在边缘接入服务，业务服务只接收标准化设备事件，不直接适配每一种 PLC 或协议。

### 6.5 数据存储与中间件基线

以下是建议基线，不代表最终选型。正式定版需通过容量、许可、团队能力和私有化适配 PoC。

| 能力 | 建议基线 | 使用原则 |
| --- | --- | --- |
| 交易数据库 | PostgreSQL 16 或 MySQL 8，组织级统一选择一种 | 服务拥有独立 Schema/数据库账号；禁止跨服务直接写表 |
| 缓存与分布式协调 | Redis | 用于缓存、短期状态和限流；不能作为财务、库存等唯一持久化来源 |
| 消息与事件 | Kafka 或 RocketMQ，PoC 后统一一种 | 事件持久化、消费重试、死信和消费延迟可观测 |
| 搜索 | OpenSearch/Elasticsearch | 用于全文检索与复杂筛选，不替代交易库权威数据 |
| 对象存储 | S3 兼容存储/MinIO | 保存图纸、附件、归档和导出文件，元数据留在业务服务 |
| 工作流 | Flowable、Camunda 等 BPMN 引擎择一 | 承载跨人/跨系统流程，不承载高频生产设备事务 |
| 分析存储 | ClickHouse、Doris 或云数仓择一 | 面向跨域明细和聚合分析，不直接承担在线交易 |
| 数据加工 | CDC + 流批一体数据管道 | 保留来源、时间和血缘；关键数据进入质量校验 |
| 密钥与凭据 | Vault/KMS 或平台等价能力 | 凭据不进入源码、镜像和普通配置文件 |

选型原则是“一类能力一个主标准”。同一阶段同时引入多种数据库、消息系统和注册中心，会显著增加私有化交付与运维成本。

### 6.6 部署架构

建议同时支持三种部署形态：

| 形态 | 适用场景 | 架构重点 |
| --- | --- | --- |
| SaaS 多租户 | 中小制造企业、标准化程度高 | 租户隔离、弹性扩容、版本统一、数据分区和租户级限流 |
| 私有化部署 | 集团、大中型制造、强合规客户 | 离线安装、软硬件兼容矩阵、升级工具、许可和本地运维 |
| 混合/边缘部署 | 多工厂、弱网、设备密集现场 | 中心管控 + 工厂边缘节点、断点续传、本地缓存和数据补传 |

中心侧建议使用 Kubernetes 管理无状态服务和 Worker，通过 Helm/Kustomize 维护环境差异，并使用 GitOps 或受控流水线发布。数据库、消息和对象存储可采用托管服务或高可用集群。

工厂边缘节点重点承载设备接入、现场缓冲、轻量 MES/WMS 执行和文件缓存。边缘与中心之间通过出站安全通道同步，必须处理网络中断、乱序、重复、时钟偏差和补传；断网期间需要明确哪些业务允许继续、哪些必须阻断。

### 6.7 安全架构

- IAM 基于 OIDC/OAuth 2.1 和企业目录对接，支持单点登录、多因素认证和账号生命周期。
- 权限采用 RBAC 为基础，并叠加组织、工厂、仓库、客户等数据范围；高敏场景可增加 ABAC 策略。
- API 网关执行身份校验、限流、签名、防重放和外部应用授权，内部服务仍需校验调用身份，不能只信任内网。
- 传输使用 TLS，敏感字段按等级进行加密、脱敏和导出控制；密钥由 KMS/Vault 管理并定期轮换。
- 业务操作、审批、权限、配置、接口和数据修正均进入不可抵赖审计链路。
- 构建流程包括依赖漏洞、镜像、源码、密钥泄漏和许可证扫描，并维护软件物料清单 SBOM。

### 6.8 可观测性与运维架构

建议基于 OpenTelemetry 统一埋点，形成四类观测信号：

1. **技术指标**：吞吐、延迟、错误率、饱和度、队列积压和资源利用率。
2. **分布式链路**：从网关到服务、消息和数据库的 Trace ID/Correlation ID。
3. **结构化日志**：带租户、组织、用户、业务单号和请求关联标识，同时执行敏感信息脱敏。
4. **业务对账**：订单未下发、消息未消费、库存账实差、报工未过账等业务异常。

可采用 Prometheus + Grafana + Loki + Tempo/Jaeger，或等价的云服务组合。告警必须有分级、值班人、处理手册和关闭条件，不能只把错误日志发送到群里。

### 6.9 交付与研发工程体系

- 代码按领域仓库或有明确边界的 Monorepo 管理，禁止按技术层建立所有产品共享的巨型工程。
- CI 至少包括编译、单元测试、契约测试、代码扫描、镜像扫描和制品签名。
- CD 支持开发、测试、预生产、生产多环境晋级，生产变更必须可审计、可灰度、可回滚。
- 数据库变更采用版本化 Migration；破坏性变更先兼容发布，再迁移数据，最后删除旧结构。
- 服务接口采用消费者驱动契约测试；跨域主链路保留自动化端到端回归。
- 客户扩展优先使用配置、规则、插件和事件订阅；确需定制时使用隔离扩展包，不修改产品主干核心代码。

## 七、微服务拆分方案

### 7.1 拆分原则

微服务以限界上下文和数据所有权为边界，不以菜单、页面、数据库表或产品缩写为边界。每个候选服务至少应满足以下多数条件后再独立部署：

- 有独立且稳定的业务语言、状态机和数据所有权。
- 可由一个团队端到端负责需求、开发、发布和运行。
- 需要独立扩缩容、故障隔离、合规隔离或边缘部署。
- 与其他模块的交互能够通过明确 API 或事件完成。
- 独立发布带来的收益高于网络、数据一致性和运维复杂度。

反之，如果两个模块总是一起修改、一起发布、共享同一事务且没有独立团队，应先保留为同一部署单元内的模块。

### 7.2 逻辑微服务清单

下表定义目标态的**逻辑服务边界**。逻辑上独立不代表首期必须独立进程；首期可按 7.3 的部署单元合并。

| 领域 | 候选服务 | 核心职责与权威数据 | 首期建议 |
| --- | --- | --- | --- |
| 访问平台 | 网关服务 | 路由、限流、外部授权、API 版本和流量审计 | 独立部署 |
| 访问平台 | 租户组织服务 | 租户、企业、组织、工厂、站点和环境配置 | 与 IAM 合并部署、模块独立 |
| 访问平台 | 身份权限服务 | 账号、身份源、登录、角色、策略和数据权限 | 独立部署 |
| 平台 | 流程任务服务 | BPM 流程实例、任务、委托、催办和流程版本 | 平台单元内模块 |
| 平台 | 主数据服务 | 主数据模型、编码、黄金记录、质量和分发 | 平台单元内模块 |
| 平台 | 文档文件服务 | 通用文件、预览、签名、水印、归档和存储策略 | 平台单元内模块；EDMS 规则单独建域 |
| 平台 | 通知服务 | 站内信、短信、邮件、企业 IM 和模板 | 平台单元内模块 |
| 平台 | 审计配置服务 | 审计、字典、参数、功能开关和配置发布 | 平台单元内模块 |
| 集成 | 集成控制服务 | 连接器配置、映射、编排、凭据和接口目录 | 集成单元 |
| 集成 | 集成运行服务 | API/消息/文件任务执行、重试、死信和对账 | 独立 Worker，可横向扩容 |
| 客户 | 客户销售服务 | 客户关系、线索、商机、活动、合同和服务过程 | 客户订单单元内模块 |
| 客户 | 客户数据服务 | 身份融合、事件、标签、分群和激活任务 | 数据分析单元，后期独立 |
| 客户 | 订单履约服务 | 订单状态、拆合、库存预占、履约路由和售后 | 核心独立服务 |
| 客户 | 门店零售服务 | 门店、班次、收银、促销结果和离线单据 | 有 POS 场景时独立/边缘部署 |
| 客户 | 渠道协同服务 | 经销商、授权、渠道订单、返利和渠道库存 | 客户订单单元内模块 |
| 产品 | 产品工程服务 | 物料设计属性、BOM、图纸关联、工艺和工程变更 | 制造单元内模块；PLM 深化后独立 |
| 计划 | 物料计划服务 | 独立需求、BOM 展开、净需求、齐套和计划订单 | 计算 Worker 与 API 分离 |
| 计划 | 高级排程服务 | 资源约束、排程模型、方案、模拟和发布计划 | 独立计算服务 |
| 制造 | 生产执行服务 | 工单、工序、派工、报工、在制品和批次追溯 | 核心独立，可部署边缘节点 |

| 制造 | 设备资产服务 | 设备台账、点检、保养、维修、备件和停机 | 制造单元内模块，资产密集场景独立 |

| 供应链 | 运输执行服务 | 运单、承运商、路线、轨迹、签收和运费依据 | 供应链单元内模块，规模化后独立 |

| ERP | 库存核算服务 | 库存台账、组织间调拨和存货核算 | 企业经营单元内模块；与 WMS 严格分界 |
| ERP | 财务成本服务 | 总账、应收应付、凭证、期间、成本和结账 | 独立部署、严格权限与审计 |
| 企业 | 人力资源服务 | 员工、岗位、入转调离、考勤薪酬和人事过程 | 企业经营单元内模块 |
| 企业 | 协同办公服务 | 公告、会议、日程、汇报和员工工作台 | 企业经营单元内模块 |
| 企业 | 受控文档服务 | 受控文件版本、发布、发放、回收和保留策略 | 与通用文件服务分层，业务规则独立 |
| 数据 | 数据接入服务 | CDC、业务事件、外部数据、质量校验和血缘 | 数据分析单元 |
| 数据 | 指标语义服务 | 指标定义、模型、数据权限、查询与订阅 | 数据分析单元，负载增长后独立 |

### 7.3 首期部署组合

首期建议将上述逻辑服务组合为 8 个部署单元，减少运维和分布式事务成本：

| 部署单元 | 包含的逻辑服务 | 数据存储建议 | 可用性重点 |
| --- | --- | --- | --- |
| 01 网关与 IAM | 网关、租户组织、身份权限 | 独立身份库、Redis | 登录和网关无单点，权限变更快速生效 |
| 02 平台公共服务 | 流程任务、主数据、文档文件、通知、审计配置 | 按模块独立 Schema + 对象存储 | 任务不丢失、主数据可追溯、文件可恢复 |
| 03 客户与订单 | 客户销售、订单履约、渠道协同；按需加入门店零售 | 客户库、订单库逻辑隔离 | 订单状态幂等、库存预占可补偿 |
| 04 经营与协同 | 采购销售、库存核算、财务成本、人力、OA、受控文档 | 财务库与人力库权限隔离 | 财务一致性、结账保护、敏感数据隔离 |
| 05 计划与制造 | 产品工程、物料计划、排程、生产、质量、设备资产 | 领域 Schema + 计划计算存储 | 现场连续性、批次追溯、计算任务隔离 |
| 06 供应链执行 | 供应商、仓储、运输 | 供应商库、仓储库、运输库逻辑隔离 | 仓储高并发、账实对账、PDA 弱网 |
| 07 集成运行 | 集成控制、运行 Worker、连接器和对账 | 配置库 + 消息存储 | 重试、死信、限流和外部系统隔离 |
| 08 数据与分析 | 客户数据、数据接入、指标语义和 BI | 对象存储/数仓/OLAP | 数据延迟、血缘、质量和查询资源隔离 |

首期的“合并部署”不能演变成无边界的大单体。每个模块仍要有独立包结构、接口、数据库 Schema、迁移脚本、所有者和自动化测试，以便后续平滑拆出。

### 7.4 服务拆分演进路径

| 阶段 | 服务形态 | 目标 |
| --- | --- | --- |
| 起步期 | 领域模块化，8 个部署单元 | 快速跑通核心闭环，控制基础设施复杂度 |
| 成长期 | 将 OMS、MES、WMS、财务、排程、集成 Worker 等高价值域独立 | 获得独立发布、扩缩容和故障隔离能力 |
| 规模期 | 按多区域、边缘工厂、数据合规和团队边界继续拆分 | 支撑多客户、多工厂和生态开放 |

满足以下任一证据时，可发起独立拆分评审：

- 单模块资源占用影响同部署单元其他业务，且无法通过进程内隔离解决。
- 发布频率或故障半径明显不同，需要独立灰度与回滚。
- 有稳定独立团队，并能承担服务全生命周期。
- 数据需要单独加密、备份、驻留或审计。
- 工厂边缘、门店或外部生态要求独立部署。
- 单一数据库已形成锁竞争、容量或维护窗口瓶颈。

### 7.5 服务通信规则

| 场景 | 推荐方式 | 示例 |
| --- | --- | --- |
| 用户等待结果的命令/查询 | 同步 REST；设置超时、限流和熔断 | 订单预占库存、校验客户状态 |
| 跨域状态通知 | 异步领域事件 | 订单已确认、工单已完工、货物已签收 |
| 长时间计算 | 异步任务 + 状态查询/回调 | MRP 运算、APS 排程、批量成本计算 |
| 大批量交换 | 对象存储文件 + 清单事件 | 历史迁移、大批量对账、外部平台账单 |
| 设备实时数据 | 边缘消息协议 + 标准事件 | 设备状态、采集点位、停机事件 |

禁止形成环形同步调用。一个用户请求跨越三个以上领域服务时，应优先考虑页面聚合、异步流程或专门的应用编排服务，而不是不断延长同步调用链。

### 7.6 分布式事务与一致性

- 单服务内使用本地 ACID 事务；跨服务不采用共享数据库事务。
- 业务状态变更与事件发布使用 Transactional Outbox/CDC，避免“数据库成功但消息丢失”。
- 跨域长事务使用 Saga/流程编排，定义正向步骤、补偿动作、超时和人工介入点。
- 所有写接口和消息消费者必须支持幂等；幂等键应来自业务单号或明确的请求标识。
- 库存、金额、数量等关键对象使用版本号或乐观锁，冲突不能静默覆盖。
- 对最终一致的数据提供状态查询、差异对账和人工修复工具。
- 财务过账、结账等不可随意补偿的场景采用明确的冲销业务，而不是直接删除或回滚历史记录。

### 7.7 数据边界规则

1. 每个服务是其业务数据的唯一写入者。
2. 服务不得直接连接其他服务数据库，也不得通过共享表完成集成。
3. 跨域查询通过 API、事件构建的本地只读投影或数据平台完成。
4. 共享数据库实例可以作为首期成本选择，但必须使用独立 Schema、账号、迁移和备份策略。
5. 主数据服务维护统一标识与治理状态，领域服务保留完成业务所需的本地快照。
6. 数据删除要满足审计和保留要求；业务历史优先使用停用、失效和冲销，而非物理删除。

### 7.8 API 与事件契约

- API 使用 OpenAPI 管理，路径包含主版本；新增字段保持向后兼容，删除或改义必须经过弃用周期。
- 事件采用“过去式业务事实”命名，例如 `SalesOrderConfirmed`，不使用含糊的 `DataChanged`。
- 事件信封至少包括 eventId、eventType、occurredAt、producer、tenantId、aggregateId、version、traceId 和 payload。
- Schema 进入契约仓库并做兼容检查；消费者不能依赖未声明字段。
- 接口目录记录所有者、调用方、SLA、权限、数据等级和弃用日期。
- 外部开放 API 与内部 API 分层，分别执行配额、签名、审计和版本策略。

### 7.9 微服务治理红线

- 不因“表多”拆服务，不把一个 CRUD 模块包装成独立微服务。
- 不建立所有服务共享的“通用业务数据库”或万能 Common Service。
- 不把 BPM 当作所有领域逻辑的执行引擎。
- 不允许服务间级联同步调用完成长流程。
- 不在没有监控、自动部署、契约测试和明确所有者时增加新服务。
- 不允许客户定制直接侵入核心服务；通过配置、插件、扩展服务或事件订阅实现。
- 不以服务数量衡量架构成熟度，以交付速度、可靠性、数据一致性和变更影响范围衡量。

## 八、数据与集成架构原则

### 8.1 数据所有权

- 每个核心业务对象只设一个权威写入域。
- 其他应用通过 API、事件或受控复制消费，不直接跨库改写。
- MDM 管理跨域实体的统一标识与治理过程，不替代所有业务属性。
- BI/CDP 从数据服务、事件或数仓读取；不以直连生产库作为长期方案。

### 8.2 集成方式

- **同步 API**：用于需要即时确认的查询和命令，例如库存预占、客户校验。
- **领域事件**：用于状态传播和解耦，例如订单已审核、工单已完工、货物已签收。
- **批量/文件**：用于遗留系统、银行、税务或大量历史数据交换。
- **数据管道**：用于分析数据的抽取、校验、建模和血缘管理。

所有接口必须具备版本、幂等键、关联 ID、错误码、重试/死信、监控和业务对账。关键跨系统流程采用 Outbox/可靠消息等方式保证业务事务与事件发布的一致性。

### 8.3 分析体系

建议建立“业务明细层—主题数据层—统一指标语义层—场景看板”的结构。业务应用可以保留本域实时看板；跨域经营指标统一进入 BI 语义层。指标必须记录定义、负责人、来源、刷新频率和适用范围。

## 九、分阶段落地路径

以下周期是通用建议，最终需根据企业规模、工厂/仓库数量、现有系统、数据质量和定制范围调整。

### 阶段 0：业务蓝图与架构定版（建议 4～6 周）

目标：先确定价值、边界和数据责任，再开始大量开发。

- 选择 3～5 条端到端主流程，如订单到回款、计划到生产、采购到付款、入库到发运、质量异常闭环。
- 完成现状系统、接口、数据和组织盘点。
- 建立产品能力地图、SoR 表、主数据清单和集成清单。
- 确定试点工厂/事业部、MVP 范围、业务指标基线和治理机制。
- 形成架构决策记录、版本路线图、实施预算级估算和风险台账。

阶段门：高层目标一致；业务负责人到位；MVP 与非目标明确；关键数据负责人已指定。

### 阶段 1：统一平台与实施底座（建议 8～12 周）

目标：让后续应用建立在同一身份、组织、主数据和集成规范上。

- 上线 IAM 基础、组织/用户同步、单点登录和权限模型。
- 建立开发、测试、预生产、生产环境与持续交付流水线。
- 建立日志、指标、链路、告警、备份和审计基线。
- 落地第一批主数据：组织、人员、客户、供应商、物料。
- 建设 iPaaS/API/消息基础与接口契约规范。
- 提供统一工作台、待办、通知、文件与流程基础能力。

阶段门：账号生命周期闭环；核心主数据可追溯；接口可观测；备份恢复演练通过。

### 阶段 2：制造企业核心闭环 MVP（建议 3～6 个月）

目标：优先跑通可度量的经营与制造闭环，而不是平均建设 23 个应用。

推荐主链路：

**客户/订单 → ERP 经营单据 → MRP/APS 计划 → MES/QMS 执行 → WMS 入出库 → ERP 成本与财务 → BI 经营分析**

建议范围：

- 客户、物料、BOM、供应商、仓库与组织等主数据。
- 销售订单、采购、库存、财务和成本的 ERP 核心范围。
- MRP 需求计算；APS 可先从关键瓶颈资源开始。
- MES 工单、派工、报工、消耗、产出与批次追溯。
- QMS 来料/过程/成品检验及不合格闭环。
- WMS 收货、上架、领料、完工入库、拣配和盘点。
- BI 只建设与试点目标直接相关的指标。

阶段门：端到端业务可追溯；账实差异可解释；关键接口可对账；试点连续稳定运行；核心岗位完成 UAT 和培训。

### 阶段 3：按行业场景扩展（建议 6～12 个月）

不同制造企业不应采用同一扩展顺序：

- **研发/项目型、按单设计 ETO**：优先深化 PLM、项目制造、变更和 EDMS。
- **消费品、门店或全渠道**：优先扩展 POS、CDP、OMS 和 TMS。
- **经销体系明显**：优先扩展渠道 DMS、CRM、SRM 和返利结算。
- **资产密集、连续生产**：优先深化 EAM、状态采集、质量和停机分析。
- **多工厂多仓**：优先强化 APS、WMS、TMS、跨组织协同和集团财务。

阶段门：新增套件有明确业务场景、负责人和收益假设；公共能力复用率满足架构要求；没有形成新的数据孤岛。

### 阶段 4：数据运营、智能优化与生态（持续）

- 建立指标运营、流程挖掘、异常预测和计划优化。
- 对稳定且高质量的数据场景引入智能助手、预测与优化算法。
- 建设供应商、经销商、客户等生态门户和开放 API。
- 按季度复盘产品采用率、流程周期、数据质量与运营成本。

AI 不应早于主数据、流程状态和业务反馈闭环。没有可靠上下文和可执行动作的“智能化”，通常只能形成演示效果。

## 十、前 90 天执行计划

### 第 1～2 周：启动与范围

- 成立决策委员会、产品架构组和业务流程组。
- 确定试点组织、核心流程、关键用户和现有系统清单。
- 记录目标指标及当前值；无法取得的指标标记为待建采集能力。

### 第 3～4 周：现状诊断

- 现场走查销售、计划、车间、质量、仓库和财务。
- 绘制端到端现状流程，标记人工断点、重复录入和信息延迟。
- 盘点主数据、接口、报表、设备连接和历史数据质量。

### 第 5～6 周：目标蓝图

- 确认五套件能力地图及一期范围。
- 完成关键对象 SoR、状态流转和跨系统责任界面。
- 形成目标流程、应用架构、集成架构与数据架构初稿。

### 第 7～8 周：MVP 与交付设计

- 用真实业务样本完成关键场景原型。
- 明确配置、开发、集成、迁移、报表和设备接入工作量。
- 定义验收用例、非功能基线、切换与回退原则。

### 第 9～10 周：平台骨架

- 建立环境、流水线、编码规范、接口规范和可观测性。
- 打通统一登录、组织用户和第一条主数据链路。
- 完成首个端到端“薄切片”，证明技术与业务闭环可行。

### 第 11～12 周：试点冲刺准备

- 排定产品待办、版本节奏和依赖关系。
- 完成试点数据清洗计划、超级用户计划和测试计划。
- 召开阶段评审，基于证据决定进入实施、调整范围或先补数据治理。

90 天的成功标准不是“23 个系统全部开工”，而是范围、边界、团队、平台骨架和一条端到端薄切片均已可验证。

## 十一、团队与治理建议

### 11.1 目标组织

- **产品组合委员会**：决定套件定位、投资优先级、版本和商业包装。
- **企业架构与数据治理组**：维护边界、SoR、主数据、集成标准和架构决策。
- **平台产品组**：IAM、BPM、MDM、iPaaS、公共体验与基础服务。
- **客户与订单产品组**：CRM、CDP、OMS、POS、DMS。
- **产品与制造产品组**：PLM、MRP、APS、MES、QMS、EAM。
- **供应链与物流产品组**：SRM、WMS、TMS。
- **企业经营产品组**：ERP、HRM、OA、EDMS。
- **数据产品组**：数据平台、指标语义、BI 与数据运营。
- **交付与客户成功组**：蓝图、实施、迁移、培训、上线与持续运营。
- **SRE/安全/质量组**：可靠性、安全、测试自动化和发布门禁。

初创或规划早期不必一次配齐九支团队，可先合并为四条工作流：平台与架构、经营与客户、制造与供应链、交付与数据；但每个关键领域仍要指定唯一产品负责人和数据负责人。

### 11.2 决策机制

- 所有跨域边界争议进入架构决策记录（ADR），写明背景、选项、结论和影响。
- 所有主数据变更由数据治理委员会定义标准，由业务数据负责人审批。
- 所有跨系统接口进入统一目录，未经契约评审不进入生产。
- 每季度进行产品组合评审：继续投入、合并、暂停或退役，而不是只追加新模块。

## 十二、商业包装与版本策略

销售目录不建议直接形成 23 个 SKU。客户更容易购买 6～10 个有业务结果的产品包，例如：

1. 核心经营 ERP。
2. 客户与渠道运营。
3. 供应与计划协同（SRM + MRP + APS）。
4. 制造运营（MES + QMS，可选 EAM）。
5. 仓储与物流（WMS + TMS）。
6. 产品研发协同（PLM + EDMS）。
7. 企业协同（HRM + OA + EDMS）。
8. 数据智能（BI + CDP 的相应能力）。
9. 数字化平台与集成服务。

平台能力初期可以作为所有套件的基础许可，不必单独制造高门槛；当开放平台、生态集成或独立治理能力成熟后，再形成单独商业版本。每个产品包应明确基础版、专业版和企业版的能力差异，避免按客户逐个定制版本分支。

## 十三、非功能基线

规划阶段必须把下列内容与功能范围一同评审：

- 多组织、多工厂、多仓、多账套及适用的多租户隔离。
- 统一认证、最小权限、数据权限、敏感字段和离职回收。
- 操作、审批、接口、配置和数据变更审计。
- 可用性、性能、容量、批处理窗口和现场弱网/离线要求。
- 备份、恢复点目标、恢复时间目标、容灾和演练频率。
- 日志、指标、链路、业务对账和告警责任人。
- 版本兼容、灰度、回滚、数据库变更和客户升级路径。
- 数据驻留、保留、销毁、隐私、电子签名及行业合规要求。
- 国际化、时区、币种、税制、单位和编码规则。

这些指标均应在项目蓝图阶段填写目标值，本文不预设虚假的统一数字。

## 十四、指标与验收框架

每个试点最多选择 5～8 个结果指标，并补充过程与质量指标。可选示例：

| 价值域 | 可选指标 | 取数建议 |
| --- | --- | --- |
| 客户与订单 | 线索转化周期、订单准时履约率、取消率 | CRM/OMS 状态事件 |
| 计划与生产 | 计划达成率、齐套率、在制周期、一次通过率 | APS/MES/QMS |
| 仓储物流 | 库存准确率、拣选准确率、准时发运率 | WMS/TMS |
| 质量 | 不合格率、CAPA 关闭周期、重复问题率 | QMS |
| 设备 | 计划保养完成率、故障停机时长、MTTR | EAM/MES |
| 经营 | 订单到回款周期、存货周转、成本差异关闭周期 | ERP/BI |
| 平台 | 账号回收及时率、接口成功率、主数据完整率 | IAM/iPaaS/MDM |
| 采用 | 活跃岗位覆盖率、关键流程线上完成率、人工补录量 | 审计与业务事件 |

每个指标要同时记录：定义、公式、粒度、数据源、刷新频率、基线值、目标值、负责人和例外规则。

## 十五、主要风险及应对

| 风险 | 典型表现 | 建议应对 |
| --- | --- | --- |
| 23 个应用同时开工 | 资源摊薄、接口先于边界、没有一个闭环上线 | 以端到端价值流分期，先薄切片再扩展 |
| ERP 成为所有系统 | 任何需求都塞进 ERP，专业执行能力弱 | 明确经营主账与专业执行系统边界 |
| 平台成为“大后台” | BPM/低代码承载所有业务逻辑 | 平台只提供公共能力，领域规则归领域应用 |
| 多系统争夺主数据 | 客户、物料、库存各有多份真相 | SoR 表、统一编码、治理流程和接口契约 |
| 过早微服务化 | 团队小但运维复杂、事务难以保证 | 领域模块化起步，满足拆分条件再独立部署 |
| 定制失控 | 每个客户一个分支，升级困难 | 配置优先、扩展点、版本治理和定制准入 |
| 只上线不运营 | 流程绕行、数据质量回落、指标无人负责 | 客户成功与季度运营机制纳入合同和组织 |
| 先做大屏后做数据 | 指标好看但无法追溯或行动 | 先对象、流程和事实，再建语义与看板 |

## 十六、规划阶段需要立即确认的事项

1. 第一目标行业和典型制造模式：MTS、MTO、ATO、ETO 或流程制造。
2. 第一条要打通的端到端价值流及业务指标基线。
3. 试点工厂、仓库、销售组织及其现有系统范围。
4. ERP 是自研核心、替换对象，还是与金蝶/用友/SAP 等既有系统集成。
5. 产品的 SaaS、私有化、混合部署与边缘部署策略。
6. 客户、供应商、物料、BOM、组织、员工的权威源和数据负责人。
7. 设备、自动化仓储、税务、银行、电商等外部集成优先级。
8. 首期商业产品包、许可方式、实施服务和运维服务边界。
9. 安全、合规、可用性、容灾和数据驻留目标。
10. 未来 12 个月可投入的产品、研发、实施和行业专家资源。

完成上述十项后，才能把本规划进一步收敛成：产品需求文档、总体架构、版本路线图、项目 WBS、报价范围和可验收的实施合同。
